# 추가 모델 후보 추천

**기존 모델 구성:** Qwen2.5-7B, Qwen2.5-32B, Llama-3.3-70B
**컴퓨트 제약:** H100 1장 (필요시 H200 1장 요청 가능)
**전제:** §4.1의 "architecture는 통제 변수가 아니고 size만 남은 축"이라는 기존 설계 논리를 깨지 않는 선에서 검토

---

## 우선순위 요약

| 순위 | 모델 | 사이즈 | 추가되는 가치 | 컴퓨트 부담 |
|---|---|---|---|---|
| 1 | **Olmo 3** | 7B, 32B | Ground-truth 오염 검증 + 기존 인용(2602.12413)과 직결 | 기존 Qwen2.5-32B와 동일 |
| 2 | **Qwen2.5-Coder** | 7B, 32B (또는 3B/14B) | 코드 특화 vs 범용 축 (같은 계열, confound 없음) | 낮음 (공식 GPTQ/AWQ 존재) |
| 3 (대안) | StarCoder2 | 3B, 7B, 15B | Ground-truth 검증 (Olmo3 대체재) | 낮음 |

## 1순위: Olmo 3 (7B, 32B)

단순히 "사이즈 하나 추가"가 아니라 설계 자체를 강화하는 선택.

- **기존 인용과의 직결.** §2.4/§2.7에서 이미 인용한 arXiv:2602.12413이 바로 Olmo3의 학습 코퍼스에서 CodeForces 문제의 78%가 semantic duplicate임을 찾아낸 논문. Olmo3를 실험 모델로 넣으면 이 초안이 빌려온 인용을 자기 실험의 출발점으로 바로 이어붙일 수 있음.
- **Ground-truth 오염 라벨 확보.** Olmo 시리즈는 최종 가중치뿐 아니라 전체 학습 데이터, 학습 과정, 체크포인트까지 함께 공개하며, Olmo 3는 7B와 32B 두 규모로 base 모델까지 공개됨. 현재 설계는 "탐지기 점수가 오염 여부를 얼마나 잘 반영하는가"를 다루면서도 정작 어떤 아이템이 진짜로 오염됐는지에 대한 ground truth가 전혀 없음(전부 탐지기 출력끼리 비교하는 구조). Olmo3는 학습 코퍼스를 직접 n-gram/semantic search로 뒤져 "이 벤치마크 문제가 실제로 학습 데이터에 있었는가"를 검증할 수 있는 유일한 후보. 이러면 Q1a("양자화가 탐지기 점수를 옮기는가")를 실제 오염 라벨과 대조해서 검증하는 서브 분석이 하나 생기고, 논문 전체 신뢰도가 크게 올라감.
- **컴퓨트 적합성.** 7B/32B 둘 다 H100 한 장 안에서 기존 Qwen2.5-32B와 동일한 조건으로 실행 가능 — 새로운 하드웨어 문제를 만들지 않음.

## 2순위: Qwen2.5-Coder (같은 사이즈대, 예: 7B/32B)

Qwen2.5-Coder-32B-Instruct는 LiveCodeBench, EvalPlus, BigCodeBench 등 이미 이 설계가 쓰는 벤치마크들에서 오픈소스 최고 성능을 기록했고, 5.5조 토큰 규모의 코드 특화 데이터로 학습됨.

- **가치:** 기존 모델 라인업(Qwen2.5-7B/32B, Llama-3.3-70B)이 전부 범용 모델인데, 같은 Qwen 계열·같은 토크나이저·같은 아키텍처를 유지하면서 "코드 특화 vs 범용"이라는 축을 architecture confound 없이 추가 가능. "코드에 더 많이 노출된 모델일수록 양자화-오염 상호작용이 다르게 나타나는가"는 지금 설계에서 자연스럽게 파생되는 질문.
- **엔지니어링 부담 낮음:** 공식 GPTQ/AWQ 체크포인트가 이미 배포되어 있어 자체 양자화가 필요 없음.

---

## 대안(3순위): StarCoder2 (3B/7B/15B)

The Stack v2 기반 완전 공개 데이터라 Olmo3와 같은 ground-truth 검증 이점이 있으나, 이 초안의 기존 인용 생태계와 직접 연결되지 않아 부가가치가 상대적으로 낮음. Olmo3를 쓸 수 없는 경우의 대안.

---

## 넣지 말아야 할 것

- **70B급 이상 모델 추가.** 지금 Llama-3.3-70B 하나도 H100/H200에서 fp16이 안 실리는 상황(이전 리뷰 참고)인데, 여기 하나 더 추가하면 같은 문제를 배가시킴.
- **Qwen3-Coder-30B/480B 같은 MoE 모델.** Qwen3-Coder는 30B, 480B 등 MoE 포맷으로 배포되는데, §4.1이 이미 "architecture는 통제 변수가 아니다"라고 선을 그어놓은 상태에서 dense↔MoE까지 섞이면 quantization이 라우팅에 미치는 영향이라는 완전히 다른 confound가 개입함. 별도 후속 연구 주제로 남겨두는 것을 권장.

---

## 비용 감각

모델 하나 추가할 때마다 §4.5.3의 base-rate 보정을 모델별로 다시 수행해야 하고, 생성량도 그대로 비례해서 증가함. 하나만 추가한다면 **Olmo3-32B**, 여유가 되면 거기에 **Qwen2.5-Coder(같은 사이즈대)**를 더하는 순서를 권장 — 각각 "ground truth 검증"과 "코드 특화 축"이라는, 기존 설계에 없던 서로 다른 종류의 가치를 추가하기 때문.
